## 4. Анализ проблемного запроса

После `pg_stat_statements_reset()` запросы Q1–Q3 выполнены по 5 раз. Самый медленный по
`mean_exec_time` — **Q1** (162,48 мс; Q3 — 118,58; Q2 — 88,04).

**План Q1 до оптимизации:**

```text
Sort  (actual time=159.710..160.642 rows=20000.00)
  Sort Method: quicksort  Memory: 2172kB
  Buffers: shared hit=2008, temp read=40 written=107
  ->  HashAggregate  (actual time=144.699..153.399 rows=20000.00)
        Group Key: c.id
        Batches: 5  Memory Usage: 8241kB  Disk Usage: 656kB   <-- сброс на диск
        ->  Hash Right Join  (actual time=4.300..70.205 rows=200002.00)
              ->  Seq Scan on orders o (actual time=0.011..11.627 rows=200000.00)
              ->  Hash  ->  Seq Scan on customers c (rows=20000.00)
Execution Time: 170.932 ms
```

**Причина медленной работы:** агрегация выполняется **после** соединения, над 200 002 строками;
20 000 групп не помещаются в `work_mem = 4 МБ` (`Batches: 5`, `Disk Usage: 656kB`,
`temp written=107`), поэтому часть хеш-таблицы сбрасывается на диск.

**Решение:** агрегировать `orders` в подзапросе **до** соединения — через JOIN проходит
не 200 000 строк, а 20 000 уже сгруппированных.

```sql
SELECT c.name,
       COALESCE(s.order_count, 0) AS order_count,
       s.revenue
FROM   customers c
LEFT   JOIN (SELECT customer_id,
                    COUNT(*)          AS order_count,
                    SUM(total_amount) AS revenue
             FROM   orders
             GROUP  BY customer_id) s ON s.customer_id = c.id
ORDER  BY s.revenue DESC NULLS LAST;
```

| Запрос | Причина медленной работы | Решение | Эффект |
|--------|--------------------------|---------|--------|
| Q1: выручка по клиентам | Агрегация 200 002 строк после `LEFT JOIN`; `HashAggregate` не помещается в `work_mem` (`Batches: 5`, 656 кБ на диск) | Агрегировать `orders` в подзапросе до JOIN | **170,93 → 98,59 мс (−42 %)**; `Batches: 5 → 1`, temp-файлы исчезли; строк в результате столько же (20 000) |

> **Проверка альтернативы.** Увеличение `work_mem` до 16 МБ убирает `Batches: 5 → 1`,
> но время не меняется (173,5 мс). Значит узкое место — не сброс на диск сам по себе,
> а объём строк, проходящих через соединение и агрегацию. Правильное решение — переписать запрос.

### 2. `Batches > 1` в Hash Join

```sql
SET work_mem='64kB'; SET enable_mergejoin=off; SET enable_nestloop=off;
EXPLAIN (ANALYZE, BUFFERS) SELECT c.name, COUNT(o.id) FROM customers c
LEFT JOIN orders o ON o.customer_id=c.id GROUP BY c.id,c.name;
```

| work_mem | Batches | Execution Time |
|---|---|---|
| 64 кБ | **8** | 467,57 мс |
| 4 МБ (по умолчанию) | 1 | 104,66 мс |

**Что означает `Batches > 1`:** хеш-таблица не помещается в `work_mem`, поэтому PostgreSQL делит её
на N частей. За один проход обрабатывается одна часть: внутреннее отношение перечитывается N раз,
растёт I/O — отсюда замедление в 4,5 раза. Увеличивать `work_mem` глобально нельзя (он выделяется
на каждый узел каждого соединения), поэтому в production его поднимают точечно через `SET LOCAL`.

> Без принудительного отключения `mergejoin`/`nestloop` планировщик на этой базе выбирает
> `Merge Left Join` по `idx_orders_customer_id` — хеш-таблицы тогда нет и `Batches` не появляется.

### 3. Почему Seq Scan, хотя индекс есть

Индекс по `status` был создан и проверен:

| Запрос | Доля строк | План |
|---|---|---|
| `WHERE status='pending'` (39 978 строк) | 20 % | `Bitmap Heap Scan` по `idx_orders_status`, 1 788 страниц, 23,9 мс |
| `WHERE status='delivered'` (40 227 строк) | 20 % | `Bitmap Heap Scan` по `idx_orders_status`, 13,2 мс |

При 20 % строк индекс **используется**: строки лежат на 1 788 страницах из 1 788, но bitmap-скан
читает каждую страницу один раз, а сам индекс — всего 6 страниц, поэтому это дешевле, чем Seq Scan
(1 788 страниц подряд + разбор 200 000 строк). Seq Scan планировщик выбирает, когда индекс не даёт
выигрыша: нужно ≥ ~30 % строк **и** строки размазаны по всем страницам, либо индекс не покрывает
условие. После перераспределения статусов в лаб. 07 (`delivered` = 85 %) индекс по `status`
перестанет помогать — это проверено там же.
