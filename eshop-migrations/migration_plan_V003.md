### Цель

Добавить справочник промокодов и возможность связать заказ с промокодом.
Расчёт скидки и изменение сумм существующих заказов в эту миграцию не входят.

### Изменения и риски

| Объект | Операция | Влияние и меры |
|---|---|---|
| `promo_codes` | `CREATE TABLE` + `INSERT` двух строк | Новый объект: блокировок на существующие таблицы нет. Проверить ограничения (`CHECK discount_pct BETWEEN 1 AND 99`, `UNIQUE code`) и значения строк. |
| `orders` | `ADD COLUMN promo_code_id INTEGER REFERENCES promo_codes(id)` | Затрагивает существующую таблицу (200 000 строк, 14 МБ) и требует `ACCESS EXCLUSIVE` на короткое время. Добавление колонки без `DEFAULT` — операция только в каталоге, таблица не переписывается. FK на пустой колонке проверять нечего. |

- Существующие заказы сохраняются, новый столбец для них — `NULL`.
- **Допустимое время ожидания блокировки:** в учебном запуске не задавалось (других сеансов не было).
  Для production: `SET lock_timeout = '5s'; SET statement_timeout = '30s';` перед `migrate` —

  в истории Flyway). Порог для production — не более нескольких секунд; при превышении

- При превышении лимитов или ошибке проверки: остановиться, вызвать ответственного,

### Стратегия при сбое и откат

- **Ошибка SQL внутри обычного транзакционного выполнения.** PostgreSQL откатит V003 целиком
  (включая запись в `flyway_schema_history`). Проверить фактическое состояние объектов
  (`to_regclass('public.promo_codes')`, `information_schema.columns`) и повторить `migrate`
  после исправления. `repair` при этом **не нужен** — он не является обязательным шагом.
- **Частичное выполнение вне транзакции** (например, при `CREATE INDEX CONCURRENTLY` в будущих
  миграциях): выяснить, что успело выполниться, устранить последствия вручную, затем
  `flyway repair` с теми же настройками и повторный `migrate`.
- **V003 применена, но обнаружен дефект.** Предпочтительно выпустить новую корректирующую
  V-миграцию, не изменяя применённый файл (иначе `validate` даст `checksum mismatch`).
- **Удаление `promo_code_id` и `promo_codes`** уничтожит связи и данные промокодов. Допустимо
  только после оценки зависимостей, сохранения нужных данных и согласования с ответственным.
  Это не штатное действие «при любой ошибке».
- **Ручное удаление объектов не отменяет успешную V003 в истории.** `repair` не делает V003
  снова ожидающей: он правит метаданные, а не схему. Чтобы применить изменение заново,
  нужна либо новая версия, либо ручная правка истории, что для production недопустимо.
- **Возврат из резервной копии:** восстановить согласованное состояние данных, схемы и истории
  Flyway (база + `flyway_schema_history` из одного дампа), учитывая потерю изменений после
  момента копирования. На стенде доступен только дамп от 2026-09-24 — см. «Предусловия».

## Runbook: деплой V003 на production

### Подготовка

1. Сделать `pg_dump -Fc eshop -f backup_pre_v003.dump` **и проверить восстановление** на копии.
2. Убедиться: `flyway info` — нет `Failed` миграций; записать список `Pending`.
3. Проверить, что в каталоге миграций нет посторонних ожидающих V-миграций
   (`migrate` без `-target` выполнит всё).
4. Установить лимиты в сеансе: `SET lock_timeout = '5s'; SET statement_timeout = '30s';`.
5. Уведомить команду в Slack/Telegram о начале деплоя.

### Выполнение

6. `flyway validate` — нет ошибок checksum.
7. `flyway migrate`
8. Проверить: `flyway info` — V003 статус `Success`.

### Проверка

9. SQL из раздела «Проверка после деплоя» этого плана.
10. Smoke-тест приложения: создать заказ без промокода, добавить промокод, привязать к заказу.

### Откат (если что-то пошло не так)

11. При ошибке SQL — разобрать сообщение, проверить состояние объектов, **не** запускать `repair` слепо.
12. При дефекте после успешного применения — выпустить корректирующую V-миграцию.
13. Если нужен полный возврат: восстановить `backup_pre_v003.dump` (данные + история Flyway вместе).
14. Ручное удаление `ALTER TABLE orders DROP COLUMN IF EXISTS promo_code_id;` / `DROP TABLE IF EXISTS promo_codes;`
    применять только после согласования: теряются связи и данные промокодов, а запись V003 в истории остаётся.

### После деплоя

15. Уведомить команду: деплой завершён, приложить фактические результаты проверок.
16. Закрыть тикет.
